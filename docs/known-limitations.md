# Known Limitations

What is mocked, deferred, or deliberately excluded — and why. Added to as work lands, so that anything incomplete is a **recorded decision** rather than a discovered gap.

## Deliberately simulated

Behaviour that is intentionally faked because a real integration is out of scope.

| Area | What is simulated | Why |
|---|---|---|
| Compliance documents | `compliance_documents` stores metadata only: document type, file name, status and reviewer. No file is uploaded, stored or scanned, and the file name is a label rather than a path to anything | FR-02 asks for "simulated document upload **or** metadata", and section 4.1 keeps real document handling out of scope. An admin can approve or reject paperwork that does not physically exist, which is what the demo needs |
| Trip tracking coordinates | `tracking_events` stores plain latitude/longitude numbers written by the application, with no live source behind them. The schema constrains them to physically possible ranges but cannot tell a real position from an invented one | Brief section 4.1 excludes live telematics and GPS providers. FR-08 asks only for tracking "simulated using mock coordinates or status progression" |

## Deferred to roadmap

Work that is specified but not built, so a team picking this up has the design ready.

| Area | Current state | What a team would need to do |
|---|---|---|
| Cloud deployment | Not built. The brief requires a reproducible **local** setup only, and section 4.1 places production-scale infrastructure out of scope. Images are stateless and env-var driven, so no application change is needed to host them elsewhere | Choose a container host, supply the same environment variables from a managed secrets store, and point `DB_URL` at a managed Postgres |
| Single entry point / reverse proxy | Not built. Each service is reached directly on its own port, which is sufficient for a local demo | Add a proxy in front of both services if the system is ever exposed beyond localhost — at which point TLS becomes a hard requirement, not an option |
| Location proximity in matching | Not built. Locations are city name strings, so matching compares cities for equality. A depot 20km outside Johannesburg does not match a Johannesburg load | Brief section 3.1 explicitly permits "matching cities/areas" instead of a distance value, and section 4.1 excludes production maps. Adding PostGIS, the geospatial extension for PostgreSQL, would put an extension dependency in every container to serve a requirement nobody made |
| Asset ownership by role | Not enforced by the database. `trucks.transporter_id` and `loads.owner_id` are guaranteed to reference a real user, but not a user holding the matching role. Writing directly to the database can create a truck owned by a Freight Owner | PostgreSQL cannot express "reference a row whose other column equals X" without a trigger or a denormalised copy of the role. Both were rejected in [ADR-2](adr/0002-data-model-and-database-architecture.md); the check lives in the service layer (#12) instead |
| Cross-table business rules | Partly closed. A `CHECK` constraint cannot read another table, so these rules live in the service layer. **Now enforced:** a tracking event can no longer be attached to a proposed match (`TrackingCoordinator`, 409, #15), and a receipt can no longer claim a decision its match does not have, since only `AcceptanceCoordinator.decide(...)` issues one and only on acceptance (#14). **Still open:** a rating can be recorded against a match that was never accepted, by a user who was not party to it | The remaining rating rules are enforced by #16, the issue that owns that behaviour. The schema still guarantees only that references exist and values are in range, not that the workflow order was followed |
| CITEXT case-insensitive equality via Spring Data derived queries | `UserRepository.findByEmail` uses an explicit `lower(u.email) = lower(:email)` comparison rather than relying on the `CITEXT` column type alone. PostgreSQL's operator resolution for `citext_column = varchar_param` does not reliably pick the case-insensitive operator once the JDBC driver types the bound parameter as `VARCHAR`, which is what a derived query method sends | The database's unique index on `email` still enforces case-insensitive uniqueness for writes regardless of this; only reads through a derived query needed the workaround. A future repository method following this same "find by a CITEXT column" shape should use the same explicit `lower()` form rather than assuming the column type alone is sufficient |
| Audit log immutability | Enforced against `UPDATE` and `DELETE` by trigger, but `TRUNCATE` bypasses row-level triggers entirely, and anyone able to drop the trigger can rewrite history | Full tamper-evidence needs either restricted database privileges or hash-chained entries, neither of which the brief asks for. The trigger stops accidental and casual modification, which is what an MVP audit trail needs to be trustworthy in a demo |
| Schema migration tooling | Not used. Migrations are numbered `.sql` files applied in filename order, with no record of what has already run and no rollback path | With one contributor, one environment and nothing deployed, a tool such as Flyway would buy consistency guarantees against a problem that cannot occur yet. This has a clear expiry: adopt a tool the first time the schema changes after something is deployed |
| Server-side secret scanning | Not built. Secrets are blocked locally at commit time by a Gitleaks pre-commit hook ([ADR 0001](adr/0001-local-secret-scanning.md)); nothing re-checks on the GitHub side, so a bypassed or uninstalled hook is not caught | Add a secret-scanning job to CI as a backstop for anyone who skipped local setup or used `--no-verify` |
| Dynamic security scanning (DAST) | Not run. Requires a deployed environment that does not exist, and the brief's security expectation is basic RBAC, validation, password hashing and no committed secrets | Stand up a deployed environment, then add a baseline passive scan before any gating |
| Local database port conflicts | `docker-compose.yml` binds Postgres to host port 5432 by default. On a machine already running another project's Postgres container (encountered during #7 development: an unrelated `wattwise_postgres` container held 5432), `docker compose up` fails with "port is already allocated" rather than silently picking another port | Set `DB_PORT` to an unused port (e.g. `DB_PORT=55432 docker compose up -d`) and point the app at the same port via `DB_URL`. Documented in the README rather than solved automatically, since automatically picking a port would make the app's own default (`DB_URL`'s `localhost:5432`) wrong without an obvious reason why |
| `docker-entrypoint-initdb.d` runs once per volume | The schema and seed data only apply the first time the container starts against an empty volume. Editing a migration file or the seed script after that has no effect until the volume is removed | `docker compose down -v && docker compose up -d` before expecting a schema or seed change to take effect. This is Postgres's own image behaviour, not something #7 built or can change |
| Acceptance and tracking endpoints have no role restriction | `POST /matches/{matchId}/decision`, `GET /matches/{matchId}/receipt` and both `/matches/{matchId}/tracking` endpoints are fully working and unauthenticated. The decision endpoint takes a caller-supplied `actorId` in place of an authenticated identity, so nothing stops one user accepting a match on another's behalf. FR-06, FR-07 and FR-08 are complete as behaviour; the missing control belongs to FR-01/RBAC. **This also means the receipt endpoint discloses the accepting party's IP address and user-agent to anyone who can guess a match id.** Capturing them is what the brief asks for; returning them to an unauthenticated caller is a consequence of there being no caller identity yet, not a deliberate choice | Add role enforcement and read the actor from the security context instead of the request body once #9 (auth/RBAC) merges. At the same time, restrict the receipt to the two parties to the match, which removes the disclosure without removing the data |
| A concurrent double-decision returns 400 rather than 409 | The already-decided guard in `AcceptanceCoordinator` is check-then-act, so two truly simultaneous accepts can both pass it. The database still holds the line: `receipts.match_id UNIQUE` rejects the second receipt, so no match ever gets two. But the loser surfaces through the `DataIntegrityViolationException` handler and gets a 400, where the ordinary sequential path gives a clear 409. A concurrent double **reject** has no unique constraint in its way, so both succeed and the audit trail gains a duplicate `MATCH_REJECTED` entry | Closing this properly needs optimistic locking (a version column on `matches`) or a conditional update, which is more machinery than a single-user demo justifies. Data integrity is never at risk; only the error code and a duplicate audit row are. Revisit if the platform ever has real concurrent users |
| A rejected match cannot be reconsidered | Deciding a match is one-way: `AcceptanceCoordinator` refuses any second decision with a 409, so a match rejected by mistake stays rejected and the pair can never be re-proposed either, because `matches_load_truck_unique` blocks a duplicate row | Deliberate for the demo, since an undo path needs its own audit semantics (who reversed what, and on whose authority) that no requirement asks for. A team wanting it should add an explicit reversal action that appends to the audit trail rather than making `decide` re-runnable |
| Tracking events have no tiebreaker in their sort order | `findByMatchIdOrderByOccurredAtAsc` sorts on `occurred_at` alone, and PostgreSQL's `now()` returns **transaction start** time rather than statement time. Every event written inside one transaction would therefore share a timestamp and come back in a non-deterministic order. This cannot happen today, because each tracking POST is its own transaction, so the order is always correct as the API is currently used | Add `id` as a secondary sort key the moment anything writes more than one event per transaction (a bulk 'seed a whole trip' endpoint being the obvious trigger). `id` is a uuidv7 and therefore already time-ordered, so it costs nothing. Not changed in #15 because the finder belongs to #6's repository layer and its existing test asserts the current method name, making this a change to another issue's surface for a fault that cannot yet occur |
| Trip status progression is not ordered | Any accepted match can jump straight to `DELIVERED` without ever being `DISPATCHED`, and can go backwards. Only the four status values are validated, not the transitions between them | The brief asks for tracking "simulated using mock coordinates or status progression" and #15's criterion is advancing through stages, neither of which requires a state machine. A team adding one should put it in `TrackingCoordinator`, where the accepted-only guard already lives |
| Matching endpoint has no role restriction | `POST /loads/{loadId}/matches` is fully working and unauthenticated: it accepts a caller-supplied `requestedBy` field in place of an authenticated identity, and has no `@PreAuthorize` or equivalent role check. FR-05 (the matching logic itself) is complete; this gap belongs to FR-01/RBAC, not FR-05 | Add role enforcement and pull `requestedBy` from the security context instead of the request body once #9 (auth/RBAC) merges. Tracked here rather than left implicit |
| Matching endpoint has no OpenAPI role annotation or shared error response | `MatchController`'s `@Operation` documents a summary and example body, but not the required role or a reference to a shared error-response schema, both of which depend on infrastructure #9 introduces | Add both once #9 merges; the summary/example body already in place do not need to change |

## Process limitations

Constraints arising from how the project is being built rather than from the code.

| Limitation | Detail | Recommended change on handoff |
|---|---|---|
| Secret scanning has **no regression test** | The hook was verified by hand when it landed (a fake key rejected, the same file accepted once cleaned), but nothing re-checks it. A later config edit or tooling upgrade could disable it silently, because a passing commit and an unscanned commit look identical | Commit the verification as a script and run it in CI, so a broken scanner fails visibly instead of quietly |
| Secret scanning is **opt-in per clone** | The hook only runs after a contributor runs `pre-commit install`, and `git commit --no-verify` skips it. Nothing verifies that either happened, so the control protects the careless but not the determined | Pair with the CI-side backstop above; a server-side check is the only version of this that cannot be opted out of |
| Pull requests require **0 approving reviews** | `main` is protected and takes changes by PR only, but GitHub does not permit approving your own pull request. On a single-contributor repository, requiring ≥1 approval would make every PR unmergeable except by admin override — which turns the protection into theatre, since the override becomes routine | Raise required approvals to **≥1** as soon as a second contributor exists. The gate structure is already in place; only the count changes |

## Technical debt

| Item | Impact | Suggested fix |
|---|---|---|
| `MatchingServiceConfig` pins `SimpleClientHttpRequestFactory` | Needed because the JDK's default `java.net.http.HttpClient` sends `Expect: 100-continue` for POST bodies, which uvicorn (matching-service's ASGI server) does not answer, silently dropping the request body. Any future call from this client that adds a request body inherits the fix automatically; a switch to a different HTTP client implementation would need to re-verify this | If matching-service's server ever changes (a different ASGI server, or fronted by a proxy that handles 100-continue), re-test whether this restriction is still needed |
| `Load`/`Truck`/`Match` were missing getters for fields that existed but had never been read | `pickupWindowStart/End`, `availableFrom/Until`, and `createdAt` were all mapped columns with no accessor, only discovered when #13 became the first code to actually need them. Not a defect in those fields, just untested surface area | When adding a new field to an entity, add its getter in the same change even if nothing calls it yet, rather than waiting for the first caller to discover it is missing |
